# Asian Buffalo 开发指挥与交付制度

版本：1.0  
生效日期：2026-08-06

## 一、指挥链

- 赵总：产品负责人和最终决策人。
- ChatGPT/Codex：项目总指挥、架构设计、任务拆分、规则冻结、审查和验收。
- Kimi Code：唯一主力开发者，负责主体业务代码、迁移和测试。
- Cursor：最终优化与收尾负责人，仅在Kimi形成发布候选版本后介入。

未经赵总重新授权，ChatGPT/Codex不得直接修改游戏业务代码；只允许维护项目管理文档、任务书、审查报告和验收记录。Cursor不得与Kimi并行修改同一开发分支。

## 二、批次开发制度

每一批开发必须具备：

1. 唯一批次编号和明确目标。
2. 固定Git基线和独立功能分支。
3. 允许修改的文件或模块范围。
4. 禁止事项和不可变规则。
5. 数据库迁移要求。
6. 必须完成的单元、接口、并发和回归测试。
7. 验收标准、回滚方案和提交要求。

Kimi Code完成一个批次后必须停止，未经审查不得自行进入下一批。

## 三、Kimi Code交付格式

每批必须提交：

- 基线SHA、功能分支和最终提交SHA。
- 修改、新增、删除文件完整清单。
- 数据库迁移及回滚说明。
- 接口清单和请求/响应示例。
- 关键事务、幂等、并发和安全设计说明。
- 测试命令、测试数量和完整结果。
- 静态检查、构建、依赖与敏感信息扫描结果。
- 未完成项、已知风险和下一批建议。

没有完整SHA、测试证据或迁移说明的交付一律不能验收。

## 四、ChatGPT/Codex审查制度

审查只接受三种结果：

- `PASS`：全部满足，允许进入下一批。
- `PASS WITH CONDITIONS`：主体通过，必须先完成列出的补充项。
- `REJECTED`：存在结构、账本、数学、安全或回归问题，退回Kimi修复。

审查必须核对：范围是否越界、规则是否被暗改、金额是否为整数、客户端是否影响开奖、账本是否平衡、幂等是否有效、测试是否真实覆盖、是否污染其他项目。

## 五、Cursor介入条件

只有同时满足以下条件，Cursor才能开始：

1. Kimi主体功能全部完成。
2. 数据库迁移在全新空库成功。
3. 自动测试、构建和基础端到端流程通过。
4. ChatGPT/Codex签发“允许Cursor接手”的书面指令。
5. 赵总未暂停或调整项目方向。

## 六、不可变规则

- 目标游戏的赔付表不能擅自修改。
- 未知的原版RTP、卷轴权重、逐线坐标不得伪装为已核验参数。
- 真实金额只使用整数最小单位，禁止浮点金额。
- 最终开奖结果只能由服务端生成和结算。
- 所有钱包业务必须幂等、可审计、可对账、可恢复。
- 不得复制目标游戏的代码、图片、声音、Logo或凭据。
- 不得修改、连接或污染ZRH及其他项目。
